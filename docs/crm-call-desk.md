# MAINHALL: приватный рабочий стол обзвона

Реализация: `ops/crm/server.py` + `index.html`, Python 3.12 standard library, SQLite. Адрес интерфейса — `https://main-hall.ru/office/`. Сервис слушает только `127.0.0.1:8791` и должен публиковаться через существующий Caddy с HTTPS.

## Функции

На одном экране: имя/фамилия, телефон, проект, бюджет, срок, цель, комментарий, список и статус разговора. Проект, бюджет и срок могут быть неизвестны. ID оператора назначается по авторизованному пользователю, прислать чужой ID в обычной форме нельзя. Оператор видит и меняет свои записи; администратор видит все, создаёт операторов и назначает ответственного за клиента. Поиск и фильтрация списка работают на загруженных записях. Выгрузка ограничена последними 5 000 записями выбранного оператора либо всей CRM для администратора; ограничение явно показано в интерфейсе.

`POST /api/enquiry` принимает реальное обращение с сайта без Basic Auth. JSON: `name` (необязательно, ≤120), `phone` (10–15 цифр, форматирование допустимо), `context` (≤200), `comment` (≤4000), `consent: true`, `website` (пустая ловушка ботов). Успех — HTTP 202 `{"ok":true}`, без раскрытия ID или персональных данных. Пустое имя получает внутреннее название «Заявка с сайта». Обращение сохраняется с `origin=website`, датой согласия, в список «Заявки с сайта» у администратора; оператор увидит его после назначения. GET этого endpoint возвращает 405.

## Развёртывание

Установить код в `/opt/mainhall-crm` (root-owned, без возможности записи сервисом). Создать системного пользователя `mainhall-crm` без login shell и каталог `/var/lib/mainhall-crm` с владельцем `mainhall-crm`, правами 700. Скопировать шаблон `mainhall-crm.service` в `/etc/systemd/system/`.

Один раз выполнить от имени сервисного пользователя:

```sh
python3 /opt/mainhall-crm/server.py --bootstrap --data /var/lib/mainhall-crm
```

Команда не выводит пароль. Первоначальный доступ случайно генерируется в `/var/lib/mainhall-crm/initial-access.json` с правами 600. Повторный bootstrap не меняет существующих пользователей и пароль. Передавать первоначальный доступ владельцу только через приватный канал; не печатать в Actions logs, не публиковать в репозитории или клиентской сборке. Операторские пароли также генерируются случайно и показываются администратору один раз после создания. Каждый пользователь может сменить свой пароль через «Мой пароль»: POST `/office/api/password` проверяет текущий пароль, требует новый длиной 14–128 символов, меняет хеш транзакционно и записывает audit без паролей. После смены старый доступ перестаёт работать; браузер повторно запрашивает новые данные. Восстановление полностью утерянного пароля требует администратора сервера.

В существующем блоке `main-hall.ru` Caddy добавить обработчики, сохранив статический root и остальные сайты:

```caddy
redir /office /office/ 308
handle /office/* {
    reverse_proxy 127.0.0.1:8791
}
handle /api/enquiry {
    reverse_proxy 127.0.0.1:8791
}
handle {
    root * /var/www/mainhall/current
    encode gzip
    file_server
}
```

Caddy передаёт `X-Forwarded-For`. Сервис доверяет последнему адресу этой цепочки только при соединении с loopback. После изменения валидировать Caddyfile до reload, `systemctl daemon-reload`, включить `mainhall-crm.service`. Порт 8791 во внешнем firewall не открывать.

## Защита и хранение

Пароли в БД — PBKDF2-HMAC-SHA256 с уникальной солью, 310 000 итераций и constant-time comparison. Основной доступ — браузерный HTTP Basic поверх HTTPS. Все ответы no-store/noindex, запрет фреймов и MIME sniffing. В UI пользовательский текст создаётся через `textContent`; в CSV нейтрализуются формулы. Запросы изменения требуют JSON и точного Origin основного сайта. Публичная форма допускает только основной домен и www, требует согласие и ограничивает размер 8 KiB, отправки — 5 попыток/IP/час; приватные запросы — 16 KiB. Данные и комментарии не пишутся в access logs. У сервиса ограничено время чтения сокета, память лимитера очищается. Публичная форма не отправляет сообщения наружу. Собственная смена пароля не меняет чужих пользователей.

SQLite и WAL лежат в приватном каталоге, права БД 600; изменения лидов и назначения пишутся в таблицу audit внутри транзакции. Персональные данные остаются на том же российском сервере. Для резервного копирования использовать SQLite online backup, затем сохранять копию с теми же ограничениями доступа. Простое копирование только `.sqlite3` при работающем WAL не гарантирует полноценную копию.

## Проверки

`python3 -m unittest discover -s tests -p test_crm.py -v`: аутентификация, безопасные заголовки, изоляция операторов при чтении/изменении/CSV, невозможность подменить владельца, CSRF/типы/размер тела/валидация, персистентность и аудит, создание оператора только администратором, одноразовый пароль, публичная заявка/согласие/назначение, ловушка ботов и лимит запросов, смена пароля с проверкой старого доступа и отсутствием секретов в аудите. Это проверка реализации; публикация, выдача первоначального доступа владельцу и проверка рабочего HTTPS должны быть подтверждены отдельно при развёртывании.
